# 공개 게임데이터 사례와 적용 판단

## 조사 범위와 결론

2026-10-12에 공개 게임 3종과 엔진·데이터 도구 2종의 공식 문서 및 프로젝트 문서를 확인했다. 공개 모딩 인터페이스·데이터 구조를 조사한 것이며, 상용 게임사의 비공개 Excel 운영 방식이나 내부 제작 도구를 확인했다는 뜻은 아니다. 게임 내부 원본이 모두 Excel이라고 가정하지 않는다.

사용자는 하드코딩 최소화, 재사용성 우선, 참조 유지, 적은 열과 시트, int와 enum 활용을 요청했다. 이 기준으로 선택한 프로젝트 규칙은 [[05 검증과 확장/게임데이터 작성과 변환 규칙]]이다. 아래는 확인된 사례와 그 사례로부터 내린 판단을 구분한다.

## 실제 게임에서 확인한 구조

| 사례 | 공개 자료에서 확인한 내용 | 프로젝트에 적용할 판단 |
| --- | --- | --- |
| Factorio | 시작 단계에서 타입별 Prototype을 수집·구성하고, 플레이 단계에서는 해당 Prototype을 수정할 수 없다. Recipe에는 재료·결과 같은 구조화된 목록이 있다. [F1][F2] | 정적 정의와 현재 HP·장탄·쿨타임 같은 실행 상태를 분리한다. 원본을 검증한 뒤 완성된 데이터 묶음을 공개한다. |
| Cataclysm: Dark Days Ahead | JSON의 `copy-from`과 추상 정의로 공통 값을 재사용한다. 타입에 따라 상속·수정 지원 범위가 다르며, 공식 문서는 과도한 상속과 긴 상속 사슬을 경계한다. [C1] | 공통 공격·효과 프로필을 ID로 명시적으로 공유한다. 성장 부모를 데이터 상속 부모로 해석하지 않는다. 암묵적인 다단계 값 상속은 초기 계약에 도입하지 않는다. |
| OpenRA | Weapon에 Projectile과 여러 Warhead를 연결한다. Warhead 종류에 따라 피해·대상·지연 등의 의미 있는 필드를 정의한다. [O1] | 무기의 전달 방식, 판정, 효과를 조합한다. 콘텐츠 ID별 if/switch보다 지원 행동·효과 종류별 처리기를 재사용한다. |

### 좁은 사례로 보는 재사용

- Factorio의 제작법에서 재료 목록과 결과 목록은 서로 다른 역할을 가진다. 시트 수를 줄인다는 이유로 두 역할을 하나의 불명확한 값으로 합치지 않는다. [F2]
- CDDA의 탄약 예시는 다른 탄약을 참조하고 일부 특성을 변경한다. 재사용은 가능하지만 부모 변경이 자식에 전파되므로 영향 범위를 확인해야 한다. 우리 프로젝트는 초기에는 명시적 프로필 공유와 복제로 그 범위를 관리한다. [C1]
- OpenRA에서 같은 무기 전달 구조에 여러 효과를 붙일 수 있다. 우리 프로젝트의 기본 베기와 후속 낙뢰도 ‘발동 사건 + 대상 + 처리’로 연결하되, 피해 출처와 기존 연쇄 제한을 유지한다. [O1]

## 엔진과 데이터 도구에서 확인한 방법

| 사례 | 확인한 내용 | 적용할 판단 |
| --- | --- | --- |
| Unreal Engine DataTable | CSV 열을 미리 정의한 행 구조체의 필드에 대응한다. 행 이름으로 조회하며, 누락·추가 필드 처리 옵션과 재가져오기가 있다. [U1] | 표의 열과 코드의 자료형 사이에 명시적 계약을 둔다. 편집 파일을 런타임에서 임의 추론하지 않는다. |
| Luban | 스키마로 타입·enum·참조·범위 등을 정의하고 데이터 및 C# 등 코드를 생성한다. Excel에서 enum 이름을 입력하고, 복합 키나 여러 입력 파일을 지원한다. [L1][L2][L3] | 스키마에서 DTO·enum·검증·참조 선택 목록을 생성한다. 기획용 파일 배치와 런타임 테이블 개수를 분리한다. |

Luban의 기능은 도구 도입 가능성을 보여주는 근거다. 이번 작업은 해당 도구를 설치·연결한 것이 아니다. 특히 한 시트에 여러 Excel Table을 배치하는 이번 프로젝트의 작성 형식은 별도 추출기가 필요하며, Luban 기본 로더가 그대로 읽는다고 가정하지 않는다. 초기 출력은 현행 프로젝트와 연결하기 쉬운 JSON 및 생성 C#으로 정한다. 외부 생성기를 도입하더라도 작성 계약을 유지할 어댑터 검증을 먼저 한다.

## 대안 비교

| 방법 | 장점 | 부담 | 이번 판단 |
| --- | --- | --- | --- |
| 콘텐츠마다 전용 코드 | 특수 구현이 빠름 | 같은 규칙 복제, 콘텐츠 추가 때 코드 변경 | 신규 동작의 처리기 구현에만 사용 |
| 모든 것을 enum으로 작성 | 자동 완성과 분기 편의 | 무기·카드 추가마다 enum 변경, 저장 번호 위험 | 닫힌 행동 종류에 사용, 콘텐츠는 int ID |
| 모든 값을 key/value 행으로 작성 | 물리 열이 적음 | 단위·필수값·참조가 약해지고 행·검색 증가 | 일반 게임 수치에는 사용하지 않음 |
| 거대한 한 표 | 한 화면에서 찾기 쉬움 | 무관한 빈 열과 중복 값, 타입 혼합 | 같은 행 의미일 때만 병합 |
| 논리 테이블마다 시트 | 참조 구조가 단순함 | 현재처럼 많은 탭을 이동 | 관련 표를 같은 작업 시트에 배치 |
| 공통 프로필 + 명시적 연결 + 생성 코드 | 재사용·검증·타입 안정성 | 스키마와 변환기 필요 | 기본 방식으로 선택 |

문자열 ID 자체가 하드코딩을 강제하지는 않는다. Unreal은 행 이름을 쓰며 CDDA의 데이터 로딩 예시는 타입이 붙은 `string_id`를 사용한다. [U1][C2] 이 프로젝트가 int를 택하는 이유는 C# 정수 조회·명시적 참조·자동 생성 체계를 일관되게 운영하기 위해서다. 근거 없이 모든 상황에서 더 빠르거나 항상 메모리를 덜 쓴다고 단정하지 않는다.

## 현재 프로젝트와의 차이

- `MythBuildData.xlsx`는 21시트의 작성용 데이터이며 문자열 ID·설명형 효과·별도 수치 행을 사용한다. 실제 계약과 검사는 [[05 검증과 확장/신화 빌드 Excel 데이터 계약]]을 따른다.
- `Assets/Scripts/FrameWork/GameDataBase.cs`에는 int 키의 Item과 string 키의 Hero가 함께 있다. Item의 `param_1` 의미가 무기 공격력·물약 회복·방어구 방어력으로 달라진다. enum 숫자 구간으로 category를 추론하는 코드도 있다. 신규 데이터 규칙에서는 의미별 필드·명시적 호환 검사를 사용한다.
- `Assets/Scripts/FrameWork/GameDataDTO.cs`는 CommonInstant·Item·Hero 로딩을 수동 등록한다. 전체 로드·참조 검증 후 공개하는 흐름은 재사용할 수 있다. 등록 목록·DTO·키 상수는 후속 생성 대상으로 둔다.
- 이번 조사는 런타임 성능 비교, 새 생성기 실행, Excel 이관 또는 Unity 플레이 시험이 아니다.
